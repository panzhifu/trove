trove 与 CloudCompare 的 PLY 加载性能对比

2026-09-11 · Arch Linux / Intel i7-12700H · CloudCompare 由 -O 命令行在 QT_QPA_PLATFORM=offscreen 下无头运行 · trove 为 release 构建 （opt-level=3, lto=thin）· 每项 3–5 次取中位数，页缓存预热
结论
  • 二进制 PLY：trove 比 CloudCompare 慢 1.9×–3.3× （500 万点：1323 ms 对 400 ms）。
  • ASCII PLY：trove 反而快约 34% （500 万点：1341 ms 对 1780 ms）——CloudCompare 的 ASCII 词法解析并不快， trove 落后的是二进制路径。
  • 瓶颈不在读文件，也不在字节解析：100 万点的 ASCII 文件比 binary 大 2.4 倍， 解析耗时却是 257.7 ms 对 264.8 ms——几乎完全相同。时间全部花在 每个顶点、每个属性的固定开销上。
  • 峰值内存是 CloudCompare 的 4–6 倍 （500 万点：320 MB 对 75 MB；CloudCompare 扣掉 123 MB 的 Qt 基线）。

3 · 为什么慢

解析耗时与「列数 × 顶点数」成正比

  • 10 万 → 100 万 → 500 万点：25.5 ms → 264.8 ms → 1308.0 ms， 严格线性，没有固定启动开销。
  • 同样 100 万点，属性从 6 列（xyz+rgb）加到 9 列（xyz+nxnynz+rgb）， 耗时 264.8 ms → 441.1 ms，1.67×，同样是线性于列数。
  • 换算下来约 44 ns / 属性，正常的内存填充应该在 1–2 ns 量级。

ASCII 与 binary 一样快 = 瓶颈不在字节

  • ASCII 100 万点 257.7 ms，binary 100 万点 264.8 ms。
  • ASCII 文件是 binary 的 2.4 倍大，还多了一次 String::from_utf8_lossy 整块拷贝，却更快。
  • 说明无论输入是 3 个浮点文本还是 12 个紧凑字节，每顶点走的都是同一套 昂贵的分配流程，真正的词法/编码开销被淹没。

代码层面的三个分配热点

crates/trove-core/src/media/mesh.rs 的 load_ply 在顶点主循环里做了这些事：

// mesh.rs:547 —— 每读一个顶点就建一个堆容器
let mut values: Vec<(String, Vec<f64>, PlyType)> =
    Vec::with_capacity(element.properties.len());

// mesh.rs:591 —— 每个属性：clone 一次属性名（堆分配）+ 一个 Vec<f64>（又一次堆分配）
values.push((property.name.clone(), v, property.ty));

// mesh.rs:593 / 603 —— 之后每个属性还要按名字线性扫描一遍
let scalar = |name: &str| values.iter().find(|(n, _, _)| n == name)…;
let channel = |names: &[&str]| values.iter().find(|(n, _, _)| …)…;

一次 500 万点的加载因此要产生约 3000 万次堆分配（5M 顶点 × 6 属性 × 2 次）和同等数量的属性名字符串比较。这正是内存也要多占 4–6 倍的原因——分配器的碎片和保留页从未还回。

次要问题：

  • mesh.rs:538 ASCII 路径对整个文件体做 from_utf8_lossy 拷贝（175 MB 文件即再复制 175 MB），随后才 split_whitespace。
  • mesh.rs:226 std::fs::read 整文件读入，没有流式路径， 超大 PLY 没有上限。
  • 整个解析是单线程；rayon 已经是 trove-core 的依赖，但这里没用上。

4 · 优化方向

优先级改动预期
P0 表头阶段就把属性名映射成列索引，主循环按列解析到目标数组，不再每顶点构造 Vec<(String, Vec<f64>)>。x/y/z 直接写 Vec<[f32;3]>。 消掉 3000 万次分配，预计二进制路径进入 100 ms 量级以内，追上或超过 CloudCompare
P0 二进制路径批量读：按行的 stride 一次取出整点，用 f32::from_le_bytes / bytemuck 而不是逐标量走 Cursor + Option。 配合上一条一起生效
P1 ASCII 路径去掉 from_utf8_lossy 整块拷贝，直接用 &[u8] 分词；按行边界切块交给 rayon 并行解析。 ASCII 100 万点有望从 258 ms 降到数十毫秒
P2 给 mesh::load 加流式/上限保护，避免超大 PLY 直接把内存吃光。 健壮性，不影响基准

5 · 复现方式

# 样本集（同一生成器，坐标 ±10 以内，避免 CloudCompare 触发坐标平移）
python3 /home/noke/.cache/trove-scratch/ply/gen.py

# trove：分离 read / parse / render 三段计时，5 次取中位数
cargo run --release -p trove-core --example ply_bench -- --iters 5 --json FILE...
# 单文件峰值内存（一进程一文件，VmHWM 是单调高水位）
cargo run --release -p trove-core --example ply_bench -- --mem FILE

# CloudCompare：无头运行，读它自己打的 [LOAD] finished 时间
QT_QPA_PLATFORM=offscreen CloudCompare -SILENT -AUTO_SAVE OFF -O FILE

# 汇总
python3 /home/noke/.cache/trove-scratch/ply/generate_report.py
