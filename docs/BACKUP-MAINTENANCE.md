# 备份与维护 (Backup & Maintenance)

> 自动备份、回收站、完整性校验、XMP 导出、字体管理 — 数据安全保障

---

## 概述

Trove 提供多层次的数据保护机制：

| 机制 | 频率 | 说明 |
|------|------|------|
| 自动备份 | 每天 | SQLite VACUUM INTO 快照 |
| 回收站 | 即时 | 删除缓冲，可恢复 |
| 完整性校验 | 手动/维护 | BLAKE3 重算比对 |
| 孤儿清理 | 维护任务 | 移除无引用 blob 与派生缓存 |
| 缩略图重建 | 手动 | 图片/字体/模型/音频的缓存重画 |
| 整包备份 | 手动 | zip 导出（配置+数据） |
| XMP 导出 | 手动/批量 | 标准 sidecar 元数据 |

---

## 自动备份

### 机制

使用 SQLite 的 `VACUUM INTO` 创建一致性快照：

```sql
VACUUM INTO '/path/to/backups/library_2026-01-15_143022.db';
```

### 策略

| 参数 | 值 | 说明 |
|------|-----|------|
| 频率 | 每天至多一次 | 避免频繁写入 |
| 保留 | 10 份 | 滚动删除最旧 |
| 位置 | `<library>/backups/` | 库目录内 |
| 命名 | `library_YYYY-MM-DD_HHMMSS.db` | 时间戳 |

### 备份内容

- ✅ 数据库快照（所有资产/标签/集合/元数据）
- ❌ 媒体 blob（可重新链接）
- ❌ 缩略图缓存（可重新生成）
- ❌ 搜索索引（可重建）

### 恢复

1. 关闭 Trove
2. 用备份文件替换 `library.db`
3. 重启 Trove

## 整包备份导出

### 导出内容

```
trove-backup.zip
├── manifest.json          # 恢复布局描述
├── config.json            # 应用配置
├── keybindings.json       # 快捷键
├── plugins/               # 插件设置
├── libraries/
│   └── <slug>/

│       ├── library.json   # 库配置
│       └── incoming/      # 收件箱
```

### 导出方式

- 素材库管理器 → "导出备份压缩包"
- File 菜单 → "导出备份压缩包…"

### 恢复方式

1. 素材库管理器 → "从备份恢复"
2. 选择 zip 文件
3. 按 manifest.json 布局恢复

## 回收站

### 数据模型

```sql
ALTER TABLE assets ADD COLUMN deleted_at TIMESTAMP;
-- 删除时设置 deleted_at，而非物理删除
```

### 操作流程

```
用户删除
    │
    ▼
设置 deleted_at = now()
从搜索结果/集合中隐藏
    │
    ├──► 恢复 → 清除 deleted_at
    │
    └──► 永久删除 → 物理删除行 + blob
```

### 回收站功能

| 功能 | 说明 |
|------|------|
| 查看 | 资源管理器"回收站"文件夹 |
| 恢复 | 右键 → 恢复（保留组织关系） |
| 永久删除 | 右键 → 永久删除 |
| 清空回收站 | 一键清空，释放空间 |
| 自动隐藏 | 入回收站的资产从最近查看中移除 |

### 空间释放

清空回收站时：
1. 删除资产行
2. 删除关联的 blob 文件
3. 删除缩略图缓存
4. 清理嵌入向量

## 完整性校验

### 校验流程

```
1. 遍历所有资产记录
2. 对每个 blob 文件重算 BLAKE3
3. 与记录的 BLAKE3 内容哈希比对
4. 不匹配 → 标记问题资产
5. 问题资产一键入回收站
```

### 触发方式

- 维护任务自动运行
- 手动触发：设置 → 维护 → 校验完整性

### 问题处理

| 问题 | 处理 |
|------|------|
| BLAKE3 不匹配 | 标记损坏，建议入回收站 |
| 文件不存在 | 标记丢失，可重新链接 |
| 权限错误 | 跳过，记录日志 |

## 孤儿清理

### 概念

派生文件（blob、缩略图、波形包络）不被任何资产引用 → 可安全删除。删错了也不丢数据：
缩略图与包络都能从媒体文件重算，blob 才是唯一不能重算的东西 —— 而它只删**没有记录引用**的那些。

### 清理流程

```
1. 存储型资产的 blob 文件在磁盘上找不到 → 该资产移入回收站（记录留着，清空回收站才真删）
2. 扫 media/ 下所有文件：内容哈希没有任何记录引用 → 删除（layout 对不上的杂乱文件同样算垃圾）
3. 扫 thumbs/：无引用的缩略图 → 删除
4. 扫 waveforms/：同样的规则删包络缓存
5. 三个目录下清空了的分片目录 → 删除
```

计数在 Settings ▸ 文件 的清理结果里逐项报出：`blobs_removed` / `thumbs_removed` /
`waves_removed` / `files_trashed` / `empty_dirs_removed`。

### 一条容易写错的规则

缩略图和包络是**按内容哈希**寻址的，而链接导入的资产在 `media/` 下**根本没有文件** ——
它的原本躺在用户指定的位置。所以"哈希在 `media/` 里找不到"对链接资产恒真，
拿它当判据会把每一个链接资产的缩略图删掉（曾经就是这样，且每跑一次删一次）。
现在的判据是：无记录引用，**或**（该哈希属于存储型资产且 blob 已不在）。

### 安全保证

- 只删库自己写的派生文件：`media/`、`thumbs/`、`waveforms/`
- 不触碰用户原始文件（链接导入的原本永远不在删除范围内）
- 维护任务中运行，UI 只按一次按钮

## 缩略图重建

Settings ▸ 文件 ▸「重建缩略图」。默认只补缺（丢了的、从没生成过的），勾上「全部重绘」会连已有的
一起重写 —— 后者是修坏缓存的手段（缓存文件写坏时看不出来，只会一直显示不出来）。

| 类型 | 卡片怎么来 | 一次重建的代价 |
|------|------|------|
| 图片 | 解码原文件后缩到 512 px 内 | 一次解码 |
| 字体 | 现画的字样本卡（三行：拉丁 / CJK / 数字） | 解析 + 排版 |
| 3D 模型 | 默认机位 rasterize 出的几何卡 | 解析或采样 |
| 音频 | 内嵌封面优先；没有就用**波形包络**画一张 512×288 的卡 | 有封面无代价；没封面且包络没缓存 → **一次 ffmpeg** |
| 视频 | ❌ 不在计划里 | 海报帧要 ffmpeg，一个曲库/片库量级会让这个任务变得很长，所以没纳入 |

两点值得知道：

- **链接导入的资产也在范围内**。它的文件不在 `media/` 下而在用户原来的位置，重建按
  `thumb::blob_path` 找过去；早先的计划只看 `rel_path`，于是**整个链接库在这一步是空转的**
  —— 清理会删掉它们的缩略图，重建又不负责补回来。
- **音频的包络只在这里（和首次播放时）生成**，导入路径不付这笔钱：见
  [MEDIA-FORMATS.md](./MEDIA-FORMATS.md) 的「音频格式」。给一个 5000 首且全无封面的曲库跑一次
  「全部重绘」，就是 5000 次 ffmpeg（除非那首歌先被预览过 —— 预览也会算包络）；跑完之后包络进了缓存，
  之后每次导入和预览都是免费的。

计数：`regenerated`（写了多少张）与 `missing_blobs`（媒体文件已找不到的资产数），在按钮旁的结果里报出。

## 重复文件查找

### 去重策略

| 层级 | 方法 | 说明 |
|------|------|------|
| 内容去重 | BLAKE3 内容哈希 | 完全相同（字节一致） |
| 视觉去重 | dHash | 视觉相近（缩放/压缩后），64 位指纹 + 汉明距离 |

### 视觉去重流程

```
1. 按 dHash 聚类（汉明距离 ≤ 阈值）
2. 每组显示为重复组
3. 用户选择保留哪个
4. 其余入回收站
```

### 操作

- 工具 → 查找重复图片
- 按组浏览
- "保留最新，其余入回收站" 一键处理

## XMP 元数据导出

### 概念

将 Trove 的元数据写入标准 XMP sidecar 文件（`.xmp`），实现与其他软件的互操作。

### 导出内容

| 字段 | XMP 属性 |
|------|---------|
| 标题 | `dc:title` |
| 描述 | `dc:description` |
| 标签 | `dc:subject` |
| 评分 | `xmp:Rating` |
| 来源 | `dc:source` |

### 导出方式

- 单个资产：检查器 → 导出 XMP
- 批量：选中多个 → 右键 → 导出 XMP
- 自动：设置中启用"自动导出 XMP"

### 文件格式

```xml
<x:xmpmeta xmlns:x="adobe:ns:meta/">
  <rdf:RDF xmlns:rdf="http://www.w3.org/1999/02/22-rdf-syntax-ns#">
    <rdf:Description
      xmlns:dc="http://purl.org/dc/elements/1.1/"
      xmlns:xmp="http://ns.adobe.com/xap/1.0/">
      <dc:title>日落海滩</dc:title>
      <dc:description>长曝光拍摄</dc:description>
      <dc:subject>
        <rdf:Bag>
          <rdf:li>风景</rdf:li>
          <rdf:li>日落</rdf:li>
        </rdf:Bag>
      </dc:subject>
      <xmp:Rating>4</xmp:Rating>
    </rdf:Description>
  </rdf:RDF>
</x:xmpmeta>
```

### 安全写入

- 原子写入（先写临时文件，再重命名）
- 全转义（防 XML 注入）
- 不破坏原文件

## 重新挖掘元数据

`services/maintenance.rs` 的 `plan_remine` / `run_remine_plan`，入口在 Settings ▸ 文件。

`metadata::mine` 只在导入管线里跑，所以**新版本加的字段对老资产永远是空的**。这条路径就是补这个：重读文件头，把
`mine` 有权威性的那几组写回去（音频 `facts.audio` + `facts.media`，字体 `facts.font`）。

三个刻意的设计：

+ **只覆盖挖掘组，其余逐键保留**。存储的 facts 里还住着视觉签名、主色板、AI 标签与标记、以及
  `unknown` 透传键；拿 `mined.facts` 整包替换会连检索指纹和 AI 输出一起删掉 —— 一个维护按钮
  造成的大规模静默数据丢失。`services::maintenance::tests::remine_preserves_everything_it_did_not_mine`
  用一条"文件读不出任何东西"的资产把这条钉住。
+ **不动 `title`**：导入时它会用内嵌标签做种子，但用户之后可能改过名。
+ **不动时长列**：`mine_audio` 早就返回 duration，存量行本来就有，无需为此给 `AssetPatch` 加字段。

代价：每个资产一次文件头读取，lofty 与 ttf-parser 都只到标签表为止 —— 不解码、不起子进程，
所以它是少数几个可以不设警告直接提供的维护操作。「强制」变体连看起来已挖掘的行也重读。

图像暂不纳入，理由与 `AudioFacts` 的键前缀约定记在 `MEDIA-FORMATS.md`。
