## asset_fts 彻底清除 + drain 性能优化（同日续）

### 1. asset_fts / FTS5 全清
HEAD 的 `SCHEMA_VERSION` 是 **7**，所以 v8~v12 都是未发布的；v2/v3 才是已发布迁移。`asset_fts` 在**已发布版本里真实存在**，因此：
- 删掉 v2/v3/v11 里的三条 `CREATE VIRTUAL TABLE asset_fts`（连同 FTS5 的 `tokenize='unicode61'/'trigram'`），
- **保留**同名 `DROP TABLE IF EXISTS`（v3/v11/v12）——存量库就是被这些 DROP 清掉的，删了就真清不掉了。
- 这样做对「终态」可证明无差异：新库从不创建；v1 库跳过 create 仍走完所有 drop；v7+ 库根本不会重跑这几条。已写进 `MIGRATIONS` 顶部注释（明说是「never edit a released migration」的例外及理由）。
- 新增回归测试 `store::tests::schema_has_no_fts5_leftovers`：`LIKE '%fts%'` 查 `sqlite_master` 必须为空（同时覆盖 FTS5 影子表），且 `search_queue` 必须存在。

### 2. 文本搜索只走 tantivy（类型层面强制）
直接**删掉 `AssetQuery::text` 字段**，而不是留一个恒为 None 的装饰。连带：
- `store::assets::build_where` 里那段 `file_name LIKE ? OR title LIKE ? OR ...` 全删；
- `store::browse.rs` 与 `library::search_assets` 里「先 set text=None 再 build_where」的两处绕行也删了；
- 依赖 LIKE 路径的两个测试（`query_text_condition_matches_tag_names`、`asset_lifecycle_*` 里的 text 段）删除/收敛，覆盖面由 tantivy 侧测试承担。
- 顺手清了一堆 FTS 化石：`rank_intersect` 上方那段断句残缺的 doc、`assets.rs` 两段悬空 doc、`tags.rs` 里一个空的 `mod tmp_trigger_debug` 调试残留、以及 12 处注释里的「FTS」措辞；`fts_*` 测试名统一改成 `search_*`。README/README.zh 的 FTS 段与存储表清单（`asset_fts` → `search_queue`）也更新了。

### 3. drain 性能（真实数字，纠正上一节）
上一节「tantivy 本体只占 0.25 ms/行」是**错的**（那是拿总耗时减掉一个假想的删除循环算出来的）。重写微基准做真隔离后（每个实验独立库、正确的 rowid、`--micro [N]` 可调规模、批次扫描）：

| 2000 行 | ms/行 |
|---|---|
| 插入 assets，autocommit | 4.49 |
| 插入 assets，单事务 | 0.048 |
| 删队列，逐行 autocommit | 3.94 |
| 删队列，单事务逐行 | 0.002 |
| 删队列，单事务单语句 | 0.003 |
| **index only（无队列流量）＝地板** | **0.117** |
| **drain 改前** | **4.463** |
| **drain 改后** | **0.122** |

改后 ≈ 地板，即 drain 已无剩余开销。端到端：1 万 drain **45 s → 633 ms**（15790 docs/s），10 万 **5.4 s**（18502 docs/s，0.054 ms/行）。查询延迟不变（1 万 avg 4.3 ms；10 万 avg 28.9 ms —— 后者是 10 万文档下的 top-2000 + 模糊查询成本，另议）。

**改法**（`search.rs::drain`）：
- 整批一个 `DELETE … WHERE rowid IN (?,…)` + `unchecked_transaction`（drain 只拿得到 `&Connection`，用不了 `Store::transaction`）。**瓶颈就是逐语句 autocommit 的 fsync**。
- 队列无 UNIQUE，同一 asset 可能在一批里出现两次 → 用 `HashMap<Uuid,bool>` 收敛成「每 asset 一个动作」，`deleted` 取 AND（live 赢），让结果与行序无关；`index_asset` 若发现 assets 行已不在则**改为主动 `remove_asset`**（原先是 no-op，配合 `asset_tag` 级联可能与 delete 标志并存而留下陈旧文档）。
- **顺序改成「先 tantivy commit，再删队列行」**（原来是先删后 commit）。这样崩在中间是「留着重做」（幂等），反过来就是静默丢更新。
- **`DRAIN_BATCH` 500 → 8000**。批次大小就是剩下的全部开销：tantivy `commit()`（flush + reader reload）约 150 ms，按批次数乘。2 万行实测：batch 500 = 0.509 ms/行，2000 = 0.139，**8000 = 0.045**（地板 0.034）。8000 个绑定变量远低于 bundled SQLite 3.50.2 的 32766；单条删除持写锁约 9 ms，远低于 busy_timeout 5 s；崩了只重做该批。
- 顺带确认：真实导入路径（`tasks/import.rs`）本来就在单事务里 16 文件/批，所以那 50 s 的 `--scale` 插入数字只是**压测助手自己用 autocommit** 造成的假象，产品侧无此问题。`--scale` 已改用单事务插入，数字才有意义。

验证：`cargo test --workspace` 197+13 全绿；`search_smoke` 59 项断言全过；`--micro` / `--micro 20000` / `--scale 10000` / `--scale 100000` 均通过且断言（两个 drain 产出文档数一致、队列清空、每资产恰好一条文档）。

## fmt 全量漂移清理 + 10 万库查询延迟优化（同日再再续）

### 0. fmt 授权变更
上一节「别直接 `cargo fmt --all`」的结论**被用户推翻**：用户明确要求「帮我修改所有的 fmt 漂移」。所以已 `cargo fmt --all` 全量跑过，64 个文件改动（5477+/5324-），`--check` 归零。**以后按新约定：允许全量 fmt。**

### 1. 10 万库查询 28.9 ms 的真正原因（不是候选数、不是模糊查询）
先用 `--profile`（新增）拆 index vs SQL，结论：**tantivy 侧只占 1–5 ms，全部开销在 SQL 求交**。再加 `TROVE_PROFILE_QUERY` 打点细化到 `drain/index/rank/page`，`rank` = 20–38 ms。

然后逐层排除（每一步都留了对照实验）：
- 在 `rank_intersect` 内部打点：**全部时间在 `rows::query_map`**，`filter`（HashSet）≈ 0。
- 顺手把解剖块写成「阶段拆分 + 计划对照表」（build / prepare / exec+map / set+filter），在 example 里裸测同一语句只要 0.06 ms（n=97）/ 2.64 ms（n=2000）—— 和真实的 22 / 36 ms 差 340 倍，说明 20 ms 不在语句本身。
- `sql_len` 露馅：真实查询多一条 **22/24 字符的 where_sql = `WHERE trashed_at IS NULL`**，我的解剖块没带。带上之后再打印 `EXPLAIN QUERY PLAN`，**根因落定**：

```
plan=["SEARCH assets USING INDEX idx_assets_trashed (trashed_at=?)"]
```

planner 选了 `idx_assets_trashed` 当驱动索引，而 `trashed_at IS NULL` 命中每个 live 行 → **求交退化成全表扫描**，所以 97 个候选也要 22 ms（跟「top-2000 候选」无关）。而且 `kind` 条件同样中招（24.5 / 39.0 ms，走 `idx_assets_kind`）—— 是查询形态的问题，不是某个条件的问题。

### 2. 修法选择（四个候选都实测过）
| 方案 | n=97（无统计） | n=2000（无统计） | 结论 |
|---|---|---|---|
| 现状 `IN list` | 21–22 ms | 35–37 ms | 基线 |
| `IN list + INDEXED BY sqlite_autoindex_assets_1` | 0.09 | 5.1 | 快，但要写内部索引名 |
| **`+` 前缀（一元加号）** | **0.08** | **5.0** | **采用** |
| `json_each(?)` join | 630 ms | 4.0 | 弃：planner 仍选 trashed 索引 + SCAN j |
| `CTE cand(id) AS MATERIALIZED (VALUES …) CROSS JOIN` | 0.16 | 6.6 | 能用但多花 1.6 ms 物化 |
| `ANALYZE` 之后（任一变体） | 0.11 | ~5.8 | 也能修，但依赖统计新鲜度 |

选 `+`：SQLite 文档化 no-op，使该条件**不能当索引源**，语义完全不变（`+trashed_at IS NULL` 仍问「是否为 null」），不依赖统计信息、不用写内部索引名。`ANALYZE` 虽然也有效，但要维护统计新鲜度，不如前者确定。

### 3. 落地
- 新增 `store::assets::WhereMode { Driving, Rejecting }`（`pub(super)`）：`build_where(conn, q, mode)` 在 `Rejecting` 下给**可索引**的列比较（kind / is_favorite / usage_status / commercial_use / rating / trashed_at）加 `+` 前缀。`query` / `query_without_count` 用 `Driving`（列表页让过滤器当驱动是对的）；`rank_intersect` 用 `Rejecting`。
- **`rank_intersect` 签名改成 `(conn, ranked, q)`**，自己 build_where —— 原来 `library.rs` / `browse.rs` 都只为了喂它而各自算一次 `where_sql`，现在调用点少了 3 行。`build_where` 顺带从 `pub(crate)` 收到 `pub(super)`（顺带修掉「`where_sql` 可能为空」的死分支：trashed 条件是恒发的）。
- **回归测试** `store::tests::ranked_where_clause_leaves_the_id_list_driving`：钉住两个模式的条件文本 + 用 `EXPLAIN QUERY PLAN` 断言「rank 子句不被任何 `idx_assets_*` 驱动」，同时断言 Driving 子句**确实**被过滤器索引驱动（否则测试是巧合）。⚠️ 踩坑：**测试里的 id 数必须上百** —— SQLite 按 IN 列表长度估价，只给 2 个 id 时 planner 反而选 id 索引，测不出问题；给 300 个才复现（复现时挑的是 `idx_assets_favorite` 而非 trashed，所以断言只能问「有没有任何过滤器索引驱动」）。

## 第三批：工具栏每帧库读 + `distinct_exts` 查询改写

**新发现的最大头**（`--profile` 新增 `per-render toolbar reads`）：`WorkspacePanel::toolbar_row` 是 `&mut self` 且每帧重建，里面 `assets::distinct_exts` 单次 **~25 ms**（`LOWER(ext)` 包住索引列 → `idx_assets_ext` 失效 → `SCAN assets` + temp B-tree）。已修：

- `distinct_exts` 改 `SELECT DISTINCT ext … ORDER BY ext`，case folding + 去重挪到 Rust（`to_ascii_lowercase`，与 SQLite 的 ASCII-only `LOWER` 语义一致）。12 种扩展名 / 10 万行：24.6 → **15.2 ms**；单测 `distinct_exts_folds_case_dedupes_and_skips_trashed` 钉语义（大小写折叠、回收站行不参与）。
- `WorkspacePanel` 加 `filter_exts: Option<(u64, Vec<String>)>` 按 generation 缓存，`format_filter` 改成吃 `&[String]`。每帧成本 → 0。

**量过但不值得动的**：`tags::list` 0.05 ms、`by_ids × 20` 0.3 ms、`AppConfig::load()`（每帧读 JSON 配置文件！）**只有 0.012 ms** —— 差点为它做无用的缓存。

`source_folders` 的 Rust 尾巴从 `entry().or_default()` 改成先 `get_mut` 再插入（避免每行一次 String 分配），**实测无可测收益**（46.9 → 44.5 ms 属噪声），瓶颈是 SQL 侧 json_extract 全扫 35 ms。语义不变，留着。

⚠️ **方法论教训（已写进 skill §9）**：压测库里所有资产都是 `ext='jpg'`，在这种退化基数上 `DISTINCT ext` 量出 **0.004 ms** vs 28 ms，看着像 8000× —— 实际是只有一个 distinct key 时 SQLite 能跳过整段相同 key。用 scratch 表（10 万行 / 12 种扩展名）复测后真收益是 1.6×。同类坑：① `plan_of` 读的是**当前** schema，先测后建索引再统一打印会全部显示新索引；② 单测里**不能**断言索引计划（6 行、甚至 400 行时 SQLite 都选 `idx_assets_trashed`，与 10 万行相反）。

**待用户拍板的迁移候选**：`CREATE INDEX … ON assets(ext) WHERE trashed_at IS NULL` —— scratch 表实测把这条查询从 24.6 ms 压到 **3.96 ms**（索引全扫描变成 index-only）。缓存已解决「每帧」，这条解决「每次导入后的首次读」。
