## 三个 P2 功能（00e4467 / a481924 / a8df908）

### AVIF / JPEG-XL 缩略图
- **JPEG-XL 零成本**：`jxl-oxide 0.12.6` 早就在依赖树里（rawler 的传递依赖），加为直接依赖 + `features = ["image"]` 即可，API 是 `jxl_oxide::integration::JxlDecoder::new(File)` → `DynamicImage::from_decoder`。
- **AVIF 没有纯 Rust 解码器**（没有成熟的纯 Rust AV1 decoder）。`image` 的 `avif` feature 只是 ravif 编码器，解码要 `avif-native` → dav1d（C，要 meson/ninja/nasm，三平台 CI 风险大）。**最终复用 HEIC 那条路**：AVIF 就是 ISOBMFF + AV1 payload，`heif-dec` 能读（本机实测 libheif 带 AV1），所以把 `heic_to_image` 改名 `heif_to_image` 一起用；libheif 没编 AV1 时自然降级为「无缩略图」。
- `probe.rs` 补了 `jxl` 的 kind（原来 `.jxl` 会被归成 Other）和 mime `image/jxl`；尺寸探测走 `JxlImage::open_with_defaults(path).width()/height()`（只读 header）。
- 测试：`ffmpeg -c:v libjxl` / `-c:v libaom-av1 -still-picture 1` 现场造样本（本机 ffmpeg 都有），缺工具就 skip。

### 复制图片到剪贴板
- 用 `arboard 3.6`，开了 `wayland-data-control`（上游非默认，Wayland 下优先于 X11；不支持的混成器仍走 XWayland）。
- **关键坑**：X11/Wayland 下剪贴板数据**由写入进程持有**，谁复制谁hosting，`Clipboard` 一 drop 内容就没了。所以 `library/clipboard.rs` 里用一个 `OnceLock<Mutex<Option<Clipboard>>>` 常驻整个会话，而不是 `set_image` 后丢掉。
- 大图按 `MAX_EDGE = 4096` 缩边再进剪贴板（RGBA raw，arboard 自己转平台格式）。
- 默认键位刻意用 **ctrl-shift-c 而不是 ctrl-c**：ctrl-c 会抢掉搜索框/内联编辑器的文本复制（同一 key context）。
- 右键菜单只对 `AssetKind::Image` 显示；代码里 `Cell` 加了 `day` 字段那套之外，controller 新增 `asset_file()` / `primary_image_file()`（顺带可被 `model_source` 复用）。

### 时间线视图
- `ViewMode` 加 `Timeline`，工具栏按钮变三态循环 Grid→List→Timeline（图标 `IconName::Calendar`，gpui-kit 有 calendar.svg）。
- `Row` 加 `header: Option<String>`：标题行就是「没有 cells 的行」，高度固定 34px，渲染时 `row.header` 有值就画标题，不用改虚拟化结构。
- `timeline_rows()`：按 `day` 降序稳定排序 → 连续同 day 分组 → 每组「标题行 + 自己的 justify 布局」。**注意 `refill_rows` 那条路径对 Timeline 要整组重建**，不能复用来冻结行形状。

### 踩坑：workspace.rs 里 `#[cfg(test)] mod tests { use super::* }` 会报 "recursion limit reached while expanding #[test]"
- 原因是 `use super::*` 把 gpui prelude 里的 `test` **属性宏**一起 glob 进来了，和标准 `#[test]` 冲突无限展开。
- 解法：测试模块里**显式导入**需要的项（`use super::{Cell, Row, ...}`），不要 glob。gpu3d.rs 能用 glob 是因为那个模块没引 gpui 的 prelude。

## 右键「打开方式」（0baa381）

- `services/open_with.rs`（新）：扫 XDG 目录下的 `.desktop` 得到候选。**没有引任何桌面工具包**，`.desktop` 就是 INI，`Exec` 的字段码按 Desktop Entry 规范自己展开（`%f %F %u %U` 换成路径、`%i` 拆成 `--icon <icon>`、`%c` 换名字、`%%` 字面量、废弃码丢弃；整行没有文件码时按规范在末尾补路径）。跳过 NoDisplay/Hidden/Terminal/非 Application。排序：精确 mime 优先于 `image/*` 通配，再按名字。目录优先级：XDG_DATA_HOME 高于 XDG_DATA_DIRS，先见到的 id 胜出。进程内 `Mutex<Option<Vec<_>>>` 缓存，`reload_catalogue()` 可清。
- **核心设计约束**：库内 blob 路径就是它的 SHA-256（`media/<hash[:2]>/<hash>.<ext>`），就地编辑会同时破坏去重和完整性校验 → `Origin::Stored` 一律走工作副本 `<config>/edit/<asset_id>/<原文件名>`（保留原名，编辑器标题才正常；`file_name` 当不可信输入处理，防路径穿越）。副本**存在就不覆盖**（否则会把用户的编辑还原成库里那份）。`Origin::Linked` 直接原地打开。
- 「导入编辑后的副本」只在 `edited_copy()` 判定有改动时出现：先比 `size_bytes`（免费），相等且 ≤32 MiB 才真去 hash（右键时在 UI 线程跑，大文件不能 hash）。导入走现成的 `jobs::import_paths_app`（永远 copy 入库，不会 link 回去）。
- 菜单：`PopupMenuItem::submenu` 套 `PopupMenu::build`；启动放在 `App::spawn` + `background_executor` 里（副本可能很大，不能在点击回调里拷）。本机实测候选：GIMP 3.2 / showFoto / G'MIC-Qt / Firefox / Edge。
- 测试 11 个（core 7 + app 4），含字段码展开、通配 vs 精确排序、副本不覆盖已编辑内容。

## PLY 点云（2cf800a）+ 顶点色（52255f4）

起因：noke 问「当前软件可以查看 ply 模型吗」，查完发现 PLY 只吃三角网格 —— 无 `face` 的点云直接 load 失败，颜色也不读。

### 点云（2cf800a）
- `Mesh` 之前隐含「必须有三角形」：`finish` 末了 `(!mesh.is_point_cloud()).then_some(mesh)`。现在分成 `finish`（网格）与 `finish_points`（点云，不筛三角形），共用 `assemble`。`is_point_cloud()` = 无三角形且有点；`primitive_count()` 点云返回点数、否则三角形数。
- **CPU**：`paint_points` 逐点画圆盘（`Target::point`，逐像素做半径判定 + 深度测试），半径 `POINT_RADIUS = 1.15` × 超采样倍数。没有法线的点用「相对模型中心的方向」当法线，点云才有体积感；正好在中心的点用 `KEY_LIGHT` 方向。
- **GPU**：instance buffer 一个点一个实例，**四角完全在 shader 里由 `vertex_index` 生成**（`vs_point` 用 6 顶点拼两个三角形，clip 空间偏移 `corner * extent * base.w`，乘 `w` 抵消透视除法所以精灵在任何深度都是固定像素大小），`fs_point` 用 `dot(offset,offset) > 1.0` 裁成圆。**主机侧零逐顶点几何**。
- uniform 加 `params2`（x = 点半径），`UNIFORM_SIZE` 176 → 192；`fs_point` 的着色和 `fs_model` 一样从 uniform 取常量（不写死），CPU/GPU 才能一致。
- `viewport3d` 的统计标签点云显示「N points」（i18n 新增 `points` 键，两文件 458 键同序）。
- **验证方式**：本机只有 llvmpipe 软件适配器，`GpuRenderer::new()` 按设计拒绝软件适配器，所以 GPU 路径**跑不起来**——只能靠 naga parse+validate + uniform offset 断言兜底，真机验证仍待 noke。CPU 路径写了临时测试渲 4000 点彩球到 PNG 肉眼确认，确认后删除（scratch 测试不进库）。
- 踩坑：`paint()` 原本开头 `if mesh.triangles.is_empty() || …` 直接返回背景，点云永远画不出来 → 拆成只判 `longest <= 0.0` 的守卫。
- 踩坑：`paint_points` 第一版想借 `Target` 的字段再 move 出去，编译不过 → 直接在自己内部构造 `Target { colors, depth, width, height, framing }`。

### 顶点色（52255f4）
- `Mesh` 加 `colors: Vec<[f32;3]>` + `has_vertex_colors()`；`finish`/`finish_points`/`assemble` 都多带一个 `colors` 参数（OBJ/STL 传 `Vec::new()`）。`assemble` 里颜色数 ≠ 顶点数就整体丢弃——半份颜色数组会把颜色配到错的点上。
- `load_ply` 的 `values` 从 `(name, Vec<f64>)` 变 `(name, Vec<f64>, PlyType)`，因为**颜色通道的含义由类型决定**：整数是 0..=255 要 ÷255，float 已经是 0..=1 原样用（新增 `PlyType::is_integer()`）。通道名取 `red`/`diffuse_red` 两套（MeshLab、CloudCompare 写后一套）。clamp 到 0..=1，坏文件也能渲。
- 颜色只有一个决定点 `render3d::base_color`（有顶点色用顶点色，否则 `MATERIAL`），CPU splat 和 GPU instance 都调它，两条路径不会漂移。`PointData` 从 6 个 f32 变 9 个（pos+normal+color，stride 24 → 36），`gpu3d.wgsl` 的 `vs_point` 多读 `@location(2) color`，`fs_point` 用 `in.color * intensity` 而不是 `u.material.rgb * intensity`。
- **三角形网格忽略顶点色**（`Mesh` 里存了，但 `VertexData` 布局没有颜色属性，缩略图也一直按材质渲）。这是刻意的：宁可存着不用，也不为了颜色去动网格管线。
- **改 stride 要同时动三处**：`PointData::STRIDE`、`gpu3d.rs` point 管线的 `vertex_attr_array!`、shader 的 `vs_point` 入参。`the_vertex_inputs_match_the_buffer_layouts` 已改成按 entry point 校验「location 个数 × 12 == stride」，漏一处就会红。
- 新增测试 6 个（core：uchar 颜色、float 颜色、`diffuse_*`、颜色不全丢弃、带色网格仍出三角形；render3d：彩色点云按自身颜色上色）。全量 **183 core + 16 app 通过**，clippy `-D warnings` 干净，fmt 通过，i18n 458/458 同序。

## PLY 加载性能基准 vs CloudCompare（11:20–11:40，纯测量，未改产品代码）

起因：noke 问「查看软件加载 ply 模型的性能，并和系统中的 CloudCompare 对比」。

产物（两个新增文件都**未提交**，仅新增、未改任何现有代码）：
- `crates/trove-core/examples/ply_bench.rs`：read / parse / render 三段分离计时，`--iters N` 中位数、`--json`、`--mem`（单文件 VmHWM）。
- `docs/ply-load-bench.html`：对比报告（表 + CSS 条形图 + 根因 + 优化建议）。
- 工具脚本全在 `/home/noke/.cache/trove-scratch/ply/`：`gen.py`(样本) `cc_bench.sh`(CC 计时) `mem_all.sh`(双方内存) `generate_report.py`(出报告)。

结论：
- **二进制 PLY：trove(read+parse) 是 CC 的 1.9–3.3×**（5M 点 1323 ms vs 400 ms；100 万点 268 vs 80）。网格 50 万顶点 209 vs 90 ms。
- **ASCII PLY：trove 反而快 ~25%**（5M 点 1341 vs 1780 ms）——CC 的 ASCII 词法解析更慢。
- **瓶颈不在字节解析**：100 万点 ascii（34.9 MiB）257.7 ms ≈ binary（14.3 MiB）264.8 ms，文件大 2.4× 耗时几乎相同。耗时严格线性于「顶点数」和「列数」（6 列→9 列 = ×1.67），约 **44 ns/属性**，正常填充应在 1–2 ns。
- **峰值内存是 CC 的 4–6×**（5M 点 320 MB vs 75 MB，已扣 CC 的 123 MB Qt 基线）。
- 根因：`load_ply` 每顶点构造 `Vec<(String, Vec<f64>, PlyType)>`（mesh.rs:547/591）→ 5M×6 属性 ×2 次 = **3000 万次堆分配**；`scalar()`/`channel()` 每顶点线性扫列名比较字符串（mesh.rs:593/603）；ASCII 整块 `from_utf8_lossy` 拷贝（mesh.rs:538）；二进制逐标量走 `Cursor`+`Option`；无并行（rayon 已是依赖）。优化方向写在报告的 P0–P2 表里。

**测量方法上的坑（下次直接复用，别重踩）**：
- CC 无头运行：`QT_QPA_PLATFORM=offscreen XDG_RUNTIME_DIR=<可写目录> CloudCompare -SILENT -AUTO_SAVE OFF -O FILE`，它跑完**自己退出**并打印 `[LOAD] finished in X s.`。⚠️ 那个时间**只有 10 ms 精度**（`0.01 s`），小文件不可用。⚠️ **不加 `-SILENT` 会挂住不退出，而且根本没加载文件**（日志里没有 "Found one cloud"），因为它卡在对话框上。
- **峰值内存绝对不要用 Python 读 `/proc/<pid>/status`**：子进程退出后变 zombie，`/proc/<pid>/` 仍在且 VmRSS 读回 0，`while poll() is None` 之外的循环永远不结束，报出来的峰值是随机的（实测恒定 133 MB ↔ 真值 198 MB）。正解是 shell 里轮询 `ps -o rss= -p PID`：进程被回收时返回**空字符串**，这才是可靠的终止信号。
- 同样不可用：`RUSAGE_CHILDREN.ru_maxrss`（恒报 ~133 MB）、`/usr/bin/time`（本机没装）、cgroup v2 `memory.peak`（`/sys/fs/cgroup` 不可写，即使 uid=0）。
- 样本坐标必须留在 ±10 以内，否则 CC 触发 global shift，两边算的就不是同一件事。

**优化方案（同日给出，noke 说「只告诉我方案，无需修改代码」——尚未实施）**：
- P0：①表头解析时把属性名编译成 `Role` 枚举（X/Y/Z/Nx..Nz/Red/Green/Blue/Skip，识别时同时吃 `red`/`diffuse_red`），主循环里不再做任何字符串比较；②顶点循环改成按列直写**预分配数组**（`positions.resize(count, …)` 后 `positions[i][0] = v`），删掉每顶点的 `Vec<(String, Vec<f64>, PlyType)>`；③二进制路径按行 stride 一次切片、`f32::from_le_bytes` 取，不要逐标量走 `Cursor`+`Option`。这三条吃掉全部 6500 万次分配和 1 亿次字符串比较。
- P1：ASCII 去掉 `from_utf8_lossy` 整块拷贝（175 MB），改字节级分词；再按 `\n` 边界切块交 rayon 并行。P2：face 索引预分配。
- **不建议**：mmap 读文件（`fs::read` 75 MB 只要 15 ms，收益 <1%）、SIMD 浮点解析。
- 重构**不能破坏的行为契约**（都写在 `mesh.rs` 的测试里，共约 12 个 PLY 测试）：无 `face` 元素→点云（`finish_points`），**声明了 face 却没三角形→报错**；颜色整数 ÷255 / 浮点原样 / clamp 0..=1；颜色或法线数 ≠ 顶点数→**整体丢弃**；未知元素与未知属性→跳过；body 提前结束→`"the PLY body ends early"`。⚠️ ASCII 路径的 token 消费顺序必须保持一致，`Skip` 属性也要照样把 token 吃掉。
