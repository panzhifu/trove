## 导入管线性能调研（用户问「导入能否改多线程」）

用户提问：导入现在是单线程，能否改多线程，并借鉴别的软件的优化方法；先出方案、确认后再改。

**结论（有实测支撑）：导入的 staging 阶段早就是 rayon 并行的，「改多线程」不是瓶颈所在；实测加线程反而变慢。**

### 实测数据（新增 `crates/trove-core/examples/import_bench.rs`）
隔离测 stage_all vs commit 两阶段：

| 负载 | stage_all | commit（串行，16/批） |
|---|---|---|
| 300 张 420×300 PNG（108 MB） | 1.98 s（152 files/s）**93%** | 0.15 s（2003 files/s）7% |
| 8 个大 PLY（941 MB） | 0.48 s（16.7 files/s）**99%** | 0.004 s（1%） |
| 混合 105 文件 | 0.95 s（110 files/s）**97%** | 0.031 s（3%） |

**线程扩展曲线（300 张 PNG，`RAYON_NUM_THREADS` 扫描）：**

| threads | 1 | 2 | 4 | 8 | 20 |
|---|---|---|---|---|---|
| stage_all | 5.60 s | 4.71 s | 4.65 s | 6.13 s | **7.07 s** |

⚠️ **线程越多越慢**：1→2/4 有轻微改善（1.2×），8/20 线程显著退化（比单线程慢 26%）。20 核机器上并行 staging 是**负收益**。

### 根因判断
- 目标盘是 **btrfs**（`/dev/nvme0n1p2[/@home/noke/Code/trove]`），且文件系统已用 81%、碎片化。
- staging 是「读源文件 → 写 blob（temp+rename）→ 写 thumbnail（temp+rename）」的写密集路径；btrfs 的 COW + 元数据锁在并发小文件写下会打架。
- 每文件要写 **2 个新文件**（blob + thumb），300 个文件 = 600 次 create+rename，全落在同一个 btrfs 子卷。
- 即：**瓶颈是文件系统并发写，不是 CPU 核数**。所以「把单线程改成多线程」方向错了。

### 真正的优化方向（按收益排序，待用户确认）
1. **收紧并行度**：rayon 全局池 20 线程对该负载过大，考虑 `ThreadPoolBuilder` 限流（如 min(4, cores)），或按磁盘类型自适应。
2. **减少写放大**：blob 已去重（同 sha 丢弃），但 thumbnail 每次都要写；可考虑把 thumb 写入批量化/延迟。
3. **commmit 阶段**目前非瓶颈（3–7%），不必动。
4. **`expand_dirs` 在 UI 线程同步跑**（`jobs.rs:178`）：大批量/深目录会卡 UI 一帧以上 — 独立于吞吐的体验问题。
5. 视频缩略图走 `ffmpeg` **同步子进程**（`thumb.rs:251`），是单文件最贵的一步；并行子进程会加剧 FS 争用。

### 关键实测数据（三档图集，i7-12700H）

| 图集 | copy+hash | thumb | colors | phash | **sum(单线程)** | **stage_all(4线程)** | 并行加速比 |
|---|---|---|---|---|---|---|---|
| 300×640×480 (35.7 MB) | 17.2 | 29.3 | 2.1 | 5.6 | 54.3 ms/文件 | 41.4 ms/文件 | **1.31×** |
| 60×2400×1600 (88 MB) | 21.3 | 58.8 | 23.4 | 38.7 | 142.5 | 57.6 | **2.47×** |
| 12×6000×4000 (111 MB) | 38.7 | 206.1 | 144.6 | 217.2 | 608.6 | 144.7 | **4.21×** |

🔴 **发现 1：staging 的并行加速比对图像大小极度敏感。** 大图 4.21×（接近 4 线程理想值），小图只有 **1.31×** —— 4 个线程里 3 个基本白给。这**修正**了「线程数与 staging 速度无关」的旧结论：那条是对**同一批小文件重测**得出的，真相是**小文件批次并行度无效（IO/元数据锁主导），大文件批次并行度有效（CPU 解码主导）**。→ 真正该做的是**按文件大小自适应并行度**，或者干脆承认小图批次瓶颈在 FS。

🔴 **发现 2：图片确实被完整解码 2 次，且随图变大而爆炸。** `color::dominant_colors`（`color.rs:22-33`）先 `image::open(path)` 全量解码、再 `.thumbnail(24,24)`。PIL 精确对照（6000×4000 JPEG）：
- 全量解码 = **120.2 ms**
- JPEG draft 缩放解码（`im.draft()`，libjpeg 只解 1/8）= **63.9 ms**（**1.9× 快**）
- 全量解码 + 缩到 512 = 136.8 ms

实测 `colors` 在大图档是 **144.6 ms/文件**，`thumb` 是 206.1 ms —— 两者加起来 350 ms，占了单文件 608 ms 的 **57%**。**修法两条**：① color 复用 thumb 已解码的图（省 ~120 ms/文件）；② color 改用 draft/缩放解码（省 ~56 ms/文件）。①收益更大但耦合 thumb+metadata；②保持模块独立、收益也过半。

🔴 **发现 3：重复导入没有任何短路，浪费一半。** `stage_all` 第二次跑同批文件需要 **0.45–0.52×** 的时间 —— 说明 `thumb::ensure` 的 sha 短路（`thumb.rs:33`）生效了，但 `metadata::mine` 和 `VisualSignature` **照旧全跑**，算完的结果在 `commit_staged` 的 dedup 分支全被丢弃。**若去重导入是常见场景，这是白扔的一半工作量。**

🟠 **发现 4：commit 进 collection 是真的贵。** 同一批文件，`commit_staged(conn, None, …)` vs `commit_staged(conn, Some(coll), …)`：

| 图集 | commit (None) | commit (into_collection) | 倍数 |
|---|---|---|---|
| small(300) | 240.6 ms | **2402.8 ms** | 10× |
| medium(60) | 16.4 | 455.6 | 28× |
| large(12) | 4.9 | 94.3 | 19× |

每次 ~7.6–8.0 ms/文件**几乎恒定**（不随批量增长）→ ⚠️ 这**推翻了**子代理猜的「`MAX(position)` 平方项」——开销是**固定的 per-file 成本**，不是 O(N²)。根源更可能是 `collections::add_asset`（`collections.rs:181-184`）那条带子查询的 INSERT + 索引维护。但无论如何，**它把 commit 从「1–2%」抬到「small 档 16%（2403/15000）」** —— 之前测 commit 都没用 `into_collection`，所以严重低估了它的真实成本。

🟡 `phash` 单文件成本不低（大图 217 ms），但它读的是 512px 缩略图，**没有重复读原图**，设计是对的。

### gpui 滚动内核（`gpui-pre-0.3.3/src/elements/list.rs`）

**结论：gpui 的判定做得好，重建做得差 —— 不做行级 dirty 追踪。**

- 触发条件在 `list.rs:1074`：`if visible_height < available_height || size.is_none()`。**可视区内所有行每帧无条件 rebuild**；过绘区已测量过的行才跳过。
- 过绘语义：尾部 = 视口高 + `overdraw`（`list.rs:1066`），头部 = 额外 400px（`list.rs:1180`）。
- **无元素缓存**：`ListState` 只存 `SumTree<ListItem>` = 行高 + focus handle（`list.rs:244-254`）。`AnyElement` 每帧随 arena 清空丢弃（`window.rs:486` arena clear）。任何昂贵构建都无法跨帧复用。
- 偏移→索引是 **B+ 树 O(log n)**（`sum_tree.rs:206` + `list.rs:924` 的 `find::<ListItemSummary>`）。
- 🔴 **宽度变 1px → 全部行高缓存作废**（`list.rs:1543-1558` 的 `SumTree::from_iter` 全量重建），O(n)。trove 的 resize / 拖 zoom slider 会踩（靠 150ms debounce 缓解）。
- 同类对比：**接近朴素 react-window，不如 Flutter/FlashList**（那两个有 element 级复用）。
- ⚠️ trove 侧自加风险：`page_guard`（`mod.rs:787`）是**每帧新建**的，配合 gpui「可视行每帧都跑闭包」，滚到接近末尾时会形成「每帧触发分页 → notify → 再一帧」的自激循环直到加载完。

### EXIF orientation 修复（用户报的 bug：竖拍手机照片缩略图躺着）

1. `thumb.rs::decode_raster`（新）：`into_decoder()` → `decoder.orientation()` → `apply_orientation`；替换原 `image::open` 兜底分支（JPEG/PNG/WebP/TIFF 全覆盖）
2. `probe.rs::image_dimensions`：同样读 decoder.orientation()，Rotate90/270/90FlipH/270FlipH 时宽高互换

### 提交 1：`perf(workspace)` — 网格 render 每帧的库读/全量拷贝
四个点，共同思路 = **按 `controller.generation` 缓存 / 惰性化**：

| # | 位置 | 修法 |
|---|---|---|
| 1 | `interactions.rs::title_label` | 整条 label 按 generation 缓存到 `WorkspacePanel.title_cache`。dock 的 `title` 在面板自己 render **之外**跑，原来每帧两跳 SQLite（`smart_collections::get` + `collections::get`）。函数从 `&self` 改 `&mut self`。 |
| 2 | `mod.rs` 的 `visible_assets` 发布 | 原来每帧 `flat_map` 全量 collect 写 `controller.visible_assets`；改成**只在 rows 真的重建时**发布（新增局部 `layout_changed`，两个重建分支各置 true）。读取点（`select_all_visible` / `select_range_to`）改走新 accessor `visible_assets()`。字段降为 `pub(crate)` + `set_visible_assets()`。 |
| 3 | `mod.rs` 快照 + `controller` 字段 | `selected_assets` 与 `VisualSearchResults` 新增的 `ids: Rc<Vec<Uuid>>` 都改成 `Rc`，每帧快照从 O(n) 分配降为 refcount bump。`DataKey.visual` / `ViewKey.visual` 同步改 `Option<Rc<Vec<Uuid>>>`（两个 key 每帧重建，原写法每帧深拷至多 CANDIDATE_CAP 个 id）。`RenameDraft.selection` 也收 `Rc`。**所有变更走 `Rc::make_mut`**，避免本轮帧持有的快照被就地改坏。 |
| 4 | `mod.rs` 的 `page_guard` | 原来是每帧新建的 `Rc<Cell<bool>>` → 每帧清零 → 只要末尾行还在屏幕上，**任何**重渲染都会再触发一次分页（导入 churn / resize / 分页自身排的帧全算），网格会自己往后走。改成面板字段 `Rc<Cell<usize>>`，**记「上次请求是哪个 `grid_loaded`」**：同一 cursor 只请求一次，落页后 cursor 变 → 自然重新武装。视图切换（`other_changed`）把它置 `usize::MAX`（因为切视图会把 `grid_loaded` 重置回首页，可能撞上已服务过的 cursor）。 |

⚠️ 学习点：`Rc<Vec<_>>` 字段的 `.clear()` 不能直接调（`E0596`），要整值替换 `= Rc::new(Vec::new())`；`std::mem::take(&mut field)` 要写成 `Rc::make_mut(&mut field)`。**`action_targets()` 返回 `Vec<Uuid>` 是 API 契约**，`Rc::clone` 会类型不符，得写 `(*self.selected_assets).clone()`。
